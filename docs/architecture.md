# Architecture

The application has three layers inside one crate. Keep them as modules until
there is a concrete reason to publish or independently version a crate.

```text
main → ui → terminal → core
         └───────────→ core
```

## Core

`core/workspace.rs` owns session identity, active focus, and the binary split
tree. Buttons and keyboard actions issue the same `Command` values. Views never
mutate tree nodes or session fields directly. IDs are opaque and monotonically
allocated; closing a pane does not make its ID available for reuse.

Horizontal splits arrange children left/right; vertical splits arrange them
top/bottom. New panes receive focus. Closing a split leaf promotes its sibling;
closing the active pane selects the first surviving leaf. Closing a session's
last pane closes the session. Closing the selected session selects its following
neighbor, or its preceding neighbor at the end. An empty workspace is valid.

`core/grid.rs` rejects zero dimensions before they reach terminal FFI.
`core/frame.rs` owns cells, grapheme clusters, colors, styles, and cursor position.
Frames are ordinary Rust data and can be shared with a renderer using `Arc`.
Equal-style adjacent cells become text runs so the preview does not create a
GPUI element for every individual cell.

## Terminal adapter

`terminal/ghostty.rs` is the only module importing `libghostty_vt`. It owns the
terminal, reusable render iterators, and responses generated by device queries.
Its public API accepts bytes and validated grid sizes and returns owned frames.
No FFI handle or borrowed snapshot reaches a component.

`terminal/workspace.rs` associates pane IDs with terminal lifetimes and cached
frames. It prepares terminals for a candidate workspace before committing that
workspace. If resource creation fails, existing terminals and layout survive.
Closing panes drops their resources; changing focus never recreates a terminal.
Feed and resize return bytes that a future PTY transport must write back.

Keep Ghostty objects on their owning thread. They are neither Send nor Sync.
For the first live-shell implementation, a PTY reader can send byte messages
to the UI thread; feed Ghostty and refresh the cached frame there. If profiling
later justifies a worker, construct and keep all Ghostty state on that worker
and send owned frames and commands across bounded channels. Do not add unsafe
Send/Sync implementations or block the UI thread on PTY reads or child exit.

## GPUI

`ui/theme.rs` supplies semantic colors, layout dimensions, and preview terminal
metrics. Components receive a theme explicitly rather than reaching into global
mutable state. `ui/components` contains composable buttons, session rows, pane
headers, empty/status states, and a terminal surface. Callers add behavior to
button elements; visual primitives do not own workspace state.

`ui/workspace.rs` composes those components and dispatches commands. It owns one
root focus handle and restores keyboard focus after a click. Bindings are
registered once in `ui/actions.rs`. Stable session and pane IDs also identify
GPUI elements so focus changes do not reset their scroll state.

The terminal surface is a preview renderer, not a complete terminal widget.
It positions text runs using provisional monospace metrics, honors foreground,
background, bold, italic, basic underline and inversion, skips wide-character
continuations, and draws a cursor indicator. It still needs measured font
metrics, viewport-driven resize, selection, mouse/key encoding, cursor shapes,
and complete decoration handling. PTY wiring should follow those boundaries
rather than putting shell process management inside a Render implementation.

## Extension rules

- Add state transitions and invariant tests in core before wiring UI controls.
- Put reusable presentation in components and semantic styling in Theme.
- Keep shell transport and process cleanup separate from layout state.
- Return errors with context; surface recoverable errors in the workspace status.
- Preserve terminal frames and runtime ownership while switching sessions.
- Keep Cargo.lock in version control and verify compatibility when updating it.
- Avoid introducing a daemon, plugin framework, or persistence format before
  implementing and validating one interactive terminal.
